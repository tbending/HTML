Phantom + cosmoSPHere

Getting started: Sedov on a GPU

From a fresh clone to Phantom’s Sedov blast wave running on a GPU, then the same run on the CPU for comparison.

Quick start sedov on NVIDIA hardware

Ensure that you have nvcc available along with a Fortran compiler. Navigate to where you want the code to be cloned.

git clone --recurse-submodules -b GPU https://github.com/tbending/phantom.git
cd phantom
PHANTOM_DIR=$PWD

Set typical system and PHANTOM options.
# Standard PHANTOM environment variables
export OMP_SCHEDULE="dynamic"
export OMP_STACKSIZE=512M
ulimit -s unlimited
export SYSTEM=gfortran # change if necessary

# example related options
export IND_TIMESTEPS=no # note: GPU=yes will force this anyway
export SETUP=sedov

Set GPU related environment variables.
# GPU toolchains need to be visible (may be set automatically)
export CUDA_HOME=$(dirname $(dirname $(command -v nvcc)))
export LD_LIBRARY_PATH=$CUDA_HOME/lib64:$LD_LIBRARY_PATH

# GPU related environment variables
export GPU=yes
export GPU_TARGET=a100 # 'hopper' is also available, for other GPUs add to Makefile_GPU

Navigate to a directory for the calculation.

$PHANTOM_DIR/scripts/writemake.sh sedov > Makefile
make; make setup
./phantomsetup blast

Adjust the contents of blast.setup if desired.

./phantomsetup blast
./phantom blast.in

Switching to a CPU only compilation should be as simple as

make clean
make GPU=no
  • GPU_TARGET: a100, hopper (GH200, H100) or mi300 (AMD MI300A). Needs nvcc with CUDA_HOME set, or hipcc with ROCM_PATH set.
  • IND_TIMESTEPS=no is required; the kernel may be cubic (default) or quintic (KERNEL=quintic).
  • The log says cosmoSPHere: use_gpu_dens = T. COSMO_GPU=0 runs the same binary on the CPU.
  • Unsupported physics stops with a FATAL message rather than running wrongly.

Checked from a fresh clone of GPU (c71abc0c4, cosmoSPHere 38e37cb) on an A100, 17 September 2026: default Sedov, 174,000 particles, 159 steps, total energy within 3×10⁻⁹ of the CPU run.

1. Clone, with the submodules

git clone --recurse-submodules -b GPU https://github.com/tbending/phantom.git
cd phantom

The GPU branch of tbending/phantom carries the GPU density and force passes. Two submodules come with it:

DirectoryWhat it is
phantom/Phantom, with the GPU interface in src/main/gpu_dens_iface.F90 and src/main/gpu_force_iface.F90
phantom/cosmoSPHere/The C++ GPU density and force passes (its phantom branch), built automatically
phantom/octree-miniapp/Cornerstone, the GPU octree

If you cloned without --recurse-submodules, run git submodule update --init in phantom/.

2. Compilers

A Fortran compiler with OpenMP, and the GPU toolchain for your card.

GPUGPU_TARGETGPU compilerTested with
NVIDIA A100a100nvccCUDA 12.5, gfortran 11.1
NVIDIA GH200 / H100 (Hopper)hoppernvccCUDA 13.0, gfortran 11.5
NVIDIA Quadro (Pascal)quadro_pascalnvccnot recently tested
AMD MI300Ami300hipcc (AMD HIP)HIP 7.2 / ROCm 7.2, gfortran 11.1

The targets are defined in build/Makefile_GPU; a new card needs only a few lines there. Before building, make the toolchain visible:

# NVIDIA: nvcc on the PATH, and the CUDA install for linking
export CUDA_HOME=$(dirname $(dirname $(command -v nvcc)))
export LD_LIBRARY_PATH=$CUDA_HOME/lib64:$LD_LIBRARY_PATH

# AMD: hipcc on the PATH, and the ROCm install for linking
export ROCM_PATH=/path/to/rocm
export LD_LIBRARY_PATH=$ROCM_PATH/lib:$LD_LIBRARY_PATH

On GH200, clang also compiles the CUDA code, but nvcc gives a 25% faster force kernel.

3. Build phantom and phantomsetup

From phantom/, build the two programs with separate make calls (one call naming both fails):

T=a100    # or hopper, mi300, quadro_pascal
OPTS="SETUP=sedov SYSTEM=gfortran GPU=yes GPU_TARGET=$T IND_TIMESTEPS=no COSMO_DIR=$PWD/cosmoSPHere"
make phantom $OPTS
make setup   $OPTS
  • SYSTEM=gfortran is needed as for any Phantom build, unless SYSTEM is set in your environment.
  • GPU=yes GPU_TARGET=… builds cosmoSPHere for your card and links it in. GPU=no (the default) is ordinary CPU Phantom.
  • IND_TIMESTEPS=no is required: the GPU path uses global timesteps, and the Sedov setup otherwise defaults to individual timesteps.
  • KERNEL may be cubic (the default for Sedov) or quintic; other kernels are refused.
  • The Sedov build is periodic (PERIODIC=yes), which the GPU path supports.

The programs appear in bin/.

4. Set up a Sedov blast

mkdir run && cd run
../bin/phantomsetup sedov      # first call: writes sedov.setup with the defaults and stops
../bin/phantomsetup sedov      # second call: writes sedov_00000.tmp and sedov.in

The defaults are npartx = 50 on a close-packed lattice, which gives 174,000 particles and runs to t = 0.1 in a few seconds on a GPU. For the benchmark size, set npartx = 100 in sedov.setup before the second call (1,368,000 particles). sedov.in already points at sedov_00000.tmp, so no renaming is needed.

5. Run on the GPU, then on the CPU

export OMP_NUM_THREADS=16 OMP_PROC_BIND=close OMP_PLACES=cores
../bin/phantom sedov.in > gpu.log
grep use_gpu_dens gpu.log      # cosmoSPHere: use_gpu_dens = T

The same binary runs the unchanged CPU path when COSMO_GPU=0 is set, which is the cleanest comparison. Each run writes its own dumps and rewrites sedov.in, so set up a second directory from scratch:

cd .. && mkdir run_cpu && cd run_cpu
../bin/phantomsetup sedov && ../bin/phantomsetup sedov
COSMO_GPU=0 ../bin/phantom sedov.in > cpu.log

What to expect. Both runs take the same number of steps (159 with the defaults), and total energy in the two .ev files agrees to a few ×10⁻⁹ at the default tolh = 1e-4. Most of the remaining difference is the h tolerance: with tolh = 1e-8 the runs agree to about 10⁻¹⁰. The timing table at the end of each log gives the cost of step, density and force; step excludes all I/O, so compare that rather than wall time.

6. Benchmark settings (Shamrock paper, arXiv:2503.09713 §5.2.3)

To measure particles per second as in the Shamrock paper’s Figure 17:

  • set up with npartx = 100 (1,368,000 particles);
  • in sedov.in, set C_cour = 0.001 and C_force = 0.001 (no leapfrog corrector iterations), and evolve five steps (nmax = 5) to make the restart, as the paper does;
  • from that restart, with tmax = dtmax = 1.000 (no dumps in the window), run twice, with nmax = 20 and nmax = 120;
  • particles/s = 1,368,000 × 100 / (step120 − step20), where step is the total step time in each log’s timing table.

Differencing two runs cancels start-up and warm-up costs.

7. What the GPU path does, and does not do yet

It runs hydrodynamics with:

  • adiabatic or isothermal gas, including locally isothermal discs, with ipdv_heating and ishock_heating;
  • cooling applied in the force pass;
  • open or periodic boundaries;
  • a single gas particle mass;
  • the M4 cubic or M6 quintic spline;
  • global timesteps;
  • external potentials, sink particles (their forces stay on the CPU) and driven turbulence;
  • disc viscosity (alphaSS).

Phantom stops with a FATAL message when the input asks for something the GPU path does not compute:

OptionWhy it is refused
individual timestepsbuild with IND_TIMESTEPS=no
MHD, dust, radiation, self-gravity, general relativitynot computed on GPU
curlv = Tcurl v is not computed; set curlv = F
physical viscosity (irealvisc > 0)not computed on GPU
sink creation, HII regions, APR, ray-traced dust temperatureneed the kd-tree, which the GPU path does not build
sinks in the tree (use_sinktree)sink–gas forces in the tree walk are not computed on GPU
boundary particles, or any other non-gas particle typethe GPU solves every particle as gas
entropy as the energy variable, track_lum, sinks with heatingchange du/dt in ways the GPU sum does not
icooling = 9, or force-pass cooling with chemistry or dust temperaturenot supported on GPU
kernels other than cubic and quinticbuild with KERNEL=cubic or quintic

Timing detail

COSMO_DENS_STATS=1 prints one line per GPU call with the device-side cost of each phase: upload, key sort, tree build, neighbour lists, the density, gradient and force kernels, and download.
